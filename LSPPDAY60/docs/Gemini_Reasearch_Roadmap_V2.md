# **Comprehensive 60-Day Technical Roadmap: AI-Powered Robotics and Edge Intelligence Integration**

## **Executive Recommendation**

The most strategic and high-yield trajectory for the 60-day intensive learning challenge (LSPP2026) is the AI-Robotics Engineer track, specifically prioritizing the intersection of modern middleware (ROS2 Jazzy), deep learning-based perception (YOLOv8), and edge embedded intelligence (micro-ROS on ESP32).1 A pure software or isolated machine learning path increasingly fails to capture the multi-disciplinary requirements of modern autonomous systems.1 Conversely, a pure embedded systems approach without high-level semantic vision integration lacks the competitive edge required in contemporary industrial automation, autonomous vehicle development, and drone engineering.1  
The proposed architecture centers on a simulation-first methodology. Hardware dependencies represent the most significant bottleneck in robotics education, often leading to mechanical troubleshooting rather than algorithmic advancement.1 By standardizing on Gazebo Harmonic—the canonical simulation environment for ROS2 Jazzy—the curriculum ensures that complex kinematic chains, physics engines, and sensor arrays can be modeled with high fidelity without requiring 3D printing facilities or a comprehensive electronics laboratory.1 The hardware footprint is deliberately restricted to a low-cost ESP32 microcontroller and basic sensors, operating strictly as an intelligent edge controller bridged to the simulation via Wi-Fi.1  
This direction leverages existing foundational competencies in C++, Python, basic machine learning, and systems programming, propelling them into a production-grade orchestration pipeline.1 The capstone project, "VisioBot," serves as the ultimate portfolio asset. It demonstrates the ability to architect a distributed cyber-physical system where heavy compute (visual perception and autonomous navigation) operates on a host machine, while localized inference and hardware actuation operate on a resource-constrained microcontroller.1 This paradigm perfectly mirrors industry standards for IoT robotics and decentralized edge computing.

## **Phase-by-Phase Learning Architecture**

The 60-day curriculum is systematically segmented into four cumulative phases. Each phase builds upon the architectural primitives established in the preceding weeks, ensuring a coherent transition from software installation to the deployment of a fully autonomous, vision-guided robotic system.

### **Phase 1: ROS2 Foundations and Simulation Architecture (Days 1–15)**

The initial phase establishes the core middleware infrastructure. The selection of ROS2 Jazzy Jalisco on Ubuntu 24.04 LTS is mandatory; legacy distributions such as ROS2 Humble are native to Ubuntu 22.04 and introduce severe dependency conflicts when forced onto modern operating systems.1  
**Week 1: Core Middleware and Inter-Process Communication (Days 1–7)**  
**Day 1: Workspace Initialization and Build Systems.** The challenge commences with the native Debian installation of the ros-jazzy-desktop package on Ubuntu 24.04.1 The underlying architecture relies on the Data Distribution Service (DDS), which handles all underlying network transport. The developer will construct a colcon workspace, understanding the structural differences between ament\_cmake for C++ packages and ament\_python for Python modules.1 The pedagogical anchor for this foundational setup is the "ROS 2 for Beginners" framework, which emphasizes strict package isolation.1 To accelerate the learning curve, the introductory modules of The Construct's "ROS2 Jazzy Crash Course" on YouTube provide a vital visual reference for workspace structuring.6  
**Day 2: Publishers, Subscribers, and the ROS2 Graph (Python).** The fundamental mechanism of ROS2 relies on asynchronous message passing over topics. The developer will construct a Python-based publisher to broadcast structured data and a corresponding subscriber node to consume it.1 The focus is on understanding ROS2 Quality of Service (QoS) profiles, specifically the differences between "Reliable" and "Best Effort" delivery mechanisms, which become critical when transitioning to lossy wireless networks later in the project.7 Command-line introspection tools, particularly ros2 topic echo and rqt\_graph, are utilized to verify data flow.1  
**Day 3: High-Performance Node Implementation (C++).** While Python offers rapid prototyping capabilities, computationally expensive algorithms in robotics necessitate C++. The developer will translate the publisher-subscriber logic into C++ utilizing the rclcpp client library.1 This day explores shared pointers, memory management within the ROS2 executor framework, and the implementation of multithreading to handle concurrent callbacks without blocking the main execution thread.6  
**Day 4: Synchronous Remote Procedure Calls via Services.** Not all robotic operations suit the continuous streaming paradigm of topics. The developer will implement ROS2 Services, which facilitate synchronous, blocking request-response communication.1 This is ideal for discrete actions, such as triggering a sensor calibration sequence or querying a localized state. The official ROS2 Jazzy tutorials serve as the primary text, augmented by practical implementation guides.1  
**Day 5: Asynchronous Preemptible Actions.** For long-running tasks, such as navigating to a distant waypoint, blocking services are inefficient. The developer will implement ROS2 Actions, which provide a non-blocking goal-execution framework that includes continuous feedback and the ability to cancel the operation mid-flight.1 The implementation of a Fibonacci action server provides a theoretical baseline before applying the concept to robotic kinematics.1  
**Day 6: Spatial Transformations and the TF2 Library.** A robotic system is essentially a collection of moving coordinate frames. The TF2 library maintains the temporal relationship between these frames (e.g., the position of the camera relative to the base chassis). The developer will write static and dynamic transform broadcasters, resolving matrix mathematics to ensure spatial consistency.1 Visualizing these coordinate frames within RViz2 is critical. Kevin Wood's dedicated YouTube tutorials on ROS2 URDF and TF2 structures provide exceptional clarity on resolving frame mismatches.9  
**Day 7: Launch Configuration and Parameter Server.** Hardcoding variables into compiled nodes represents poor architectural design. The developer will author Python-based launch files (.launch.py) to instantiate multiple nodes simultaneously, remap topic namespaces dynamically, and inject configuration variables via YAML parameter files.1 This parameterization allows for rapid tuning of the robot's behavior without recompilation.1 Kevin Wood's "ROS2 Launch File Tutorial" on YouTube perfectly encapsulates the syntax and structural best practices for these scripts.12  
**Week 2-3: Robot Modeling, Simulation, and Autonomous Navigation (Days 8–15)**  
**Days 8–9: Unified Robot Description Format (URDF).** The transition from software to simulated hardware requires a mathematical model of the robot. The developer will author a URDF XML file defining a differential-drive chassis.1 This requires meticulous definition of \<link\> elements (incorporating mass, inertia tensors, collision meshes, and visual geometry) and \<joint\> elements (defining rotational limits and axes of actuation).1 The robot\_state\_publisher node consumes this URDF to broadcast the robot's physical state across the TF2 tree.  
**Day 10: Gazebo Harmonic Migration and Instantiation.** Gazebo Classic is deprecated; ROS2 Jazzy officially targets Gazebo Harmonic.2 The simulation environment utilizes an Entity-Component-System (ECS) architecture. The developer will utilize the ros\_gz\_bridge and ros\_gz\_sim packages to spawn the URDF model into a physics-enabled world.13 Virtual sensors, specifically a simulated GPU-accelerated 2D LiDAR and an RGB camera, are attached to the model.1 Aleksandar Haber's YouTube tutorial detailing the specific nuances of installing Gazebo Harmonic inside a ROS2 Jazzy environment resolves common initialization rendering errors and plugin detection failures.14  
**Day 11: Simultaneous Localization and Mapping (SLAM).** The system transitions from a static model to an exploratory agent. The ros-jazzy-slam-toolbox package is integrated to process the simulated LiDAR scans and odometry data.1 Operating via the Karto scan matcher and pose-graph optimization, SLAM Toolbox incrementally builds a 2D occupancy grid map of the environment.16 The developer will teleoperate the robot, observing the map generation in real-time within RViz2, and utilize the /slam\_toolbox/save\_map service to serialize the finalized map to disk.15 Kevin Wood's "ROS2 SLAM Toolbox Tutorial" on YouTube provides an exact walkthrough of the parameter tuning required for accurate loop closure.17  
**Days 12–13: The Nav2 Navigation Stack.** With a map established, the robot requires autonomous traversal capabilities. The Navigation 2 (Nav2) stack is configured, which relies on behavior trees to orchestrate complex navigation tasks.1 Global and local costmaps are parameterized to inflate obstacles, while the DWB local planner is tuned to calculate the kinematic velocity commands required to reach a target.1 The developer tests the system by issuing PoseStamped coordinate goals via the RViz2 interface, monitoring the algorithm as it dynamically routes around simulated dynamic obstacles.1 Kevin Wood's Nav2 mobile robot simulation tutorial directly supports the necessary cmd\_vel remapping and costmap configurations.19  
**Days 14–15: Phase 1 Capstone Integration.** The foundational phase concludes by uniting SLAM and Nav2. The simulated robot must autonomously explore an unknown Gazebo environment, utilizing frontier exploration or teleoperated mapping, followed immediately by an automated transition into localization (AMCL) mode for precise point-to-point navigation.1 This validates the entire kinematic and control pipeline.

### **Phase 2: Computer Vision for Robotics (Days 16–30)**

Phase 2 shifts the paradigm from spatial navigation based on LiDAR to high-level semantic understanding based on visual perception, transforming pixel arrays into actionable robotic intelligence.  
**Days 16–22: Image Pipelines and 2D Object Detection**  
**Day 16: Camera Drivers and the CvBridge Matrix.** To process visual data, the raw byte streams from the simulated Gazebo camera (or a physical USB webcam) must be translated into a usable format. The ros-jazzy-v4l2-camera package acts as the device driver, publishing sensor\_msgs/Image payloads.21 Because ROS2 image messages are incompatible with standard computer vision libraries, the cv\_bridge library is utilized within a Python node to safely convert the payload into OpenCV-compatible numpy.ndarray matrices, handling color space conversions (e.g., BGR8 to RGB).1  
**Days 17–18: YOLOv8 Semantic Inference Engine.** The system is equipped with the Ultralytics YOLOv8 deep learning architecture for real-time object detection.1 The developer will construct a dedicated ROS2 perception node that subscribes to the cv\_bridge output, passes the tensor through the YOLOv8 neural network using PyTorch, and extracts the resulting bounding box coordinates, class labels, and confidence scores.5 These outputs are wrapped in custom ROS2 messages and published to a new topic (e.g., /yolo/detections).1 To visualize the pipeline, a secondary node overlays the bounding boxes onto the original image and republishes it for RViz2 viewing.25 The "YOLOv8 ROS2 Jazzy tutorial" by robot mania on YouTube illustrates this exact bounding box orchestration.25  
**Days 19–20: Temporal Object Tracking (SORT).** Standard object detection lacks temporal memory; an object detected in frame one is mathematically unrelated to the object in frame two. To enable persistent tracking, the Simple Online and Realtime Tracking (SORT) algorithm is implemented.1 SORT utilizes Kalman filters to predict the future position of a bounding box and the Hungarian algorithm to associate detections across consecutive frames.1 The ROS2 node is upgraded to publish consistent tracking IDs, allowing the robot to "lock on" to a specific target despite temporary occlusions.  
**Day 21: ArUco Fiducial Marker Pose Estimation.** While YOLO provides semantic context, it lacks precise metric depth and orientation. The ros2\_aruco package is deployed to detect ArUco fiducial markers (e.g., DICT\_5X5\_250).1 By leveraging the known physical geometry of the printed marker, the OpenCV solvePnP algorithm calculates the exact 3D translation and rotation vectors of the marker relative to the camera lens.29 This node publishes high-precision PoseArray messages, which are fundamentally superior for close-quarters docking or manipulation.28 Kevin Wood's ArUco marker detection YouTube tutorial perfectly contextualizes the generation and 6D pose estimation of these matrices.30  
**Day 22: Event-Driven Synthesis and Audio Feedback.** Perception data is routed into actionable logic. A simple state-machine node is developed that subscribes to both YOLO and ArUco topics. Upon detecting a specific target (e.g., "person" or Marker ID 42), the node triggers a system-level command, such as playing an audio file via the sound\_play package or utilizing standard Linux text-to-speech utilities.1 This solidifies the concept of perception-driven event triggering.  
**Days 23–30: 3D Depth Estimation and Visual Servoing**  
**Days 23–24: Monocular Depth Inference.** Robots navigate in 3D space, but standard cameras provide only 2D pixel grids. To resolve this without hardware stereo cameras, AI-driven monocular depth estimation is implemented.1 Models such as MiDaS or the newer Depth Anything V3 architectures are loaded into the ROS2 node.32 These transformer-based networks analyze monocular RGB inputs and infer a relative depth map based on visual priors.31 The node publishes a normalized grayscale image where pixel intensity correlates to estimated distance.33  
**Day 25: Point Cloud Projections.** The 2D depth map is mathematically projected into a 3D coordinate space.1 Utilizing the camera's intrinsic calibration matrix (focal length and optical center), the ROS2 node translates the pixels into a sensor\_msgs/PointCloud2 format.1 The Point Cloud Library (PCL) is then applied to filter the massive data stream, utilizing voxel grids to downsample the cloud and removing statistical outliers to provide a clean 3D representation of the environment for RViz2.1  
**Days 26–27: Image-Based Visual Servoing (IBVS).** The pinnacle of vision-driven robotics is closed-loop visual control. The developer will engineer an IBVS node.1 Unlike Nav2, which plans a route on a global map, visual servoing uses the camera feed directly as the error signal. The node calculates the offset between the centroid of a YOLOv8 bounding box and the center of the camera frame.36 A Proportional-Integral-Derivative (PID) controller processes this pixel error and generates continuous /cmd\_vel rotational and linear velocities to aggressively center the object within the robot's field of view.1  
**Days 28–30: Phase 2 Capstone Integration.** The computer vision architecture is unified. The Gazebo simulation is populated with specific target objects. The robot utilizes Nav2 to patrol a sequence of waypoints. Simultaneously, the YOLOv8 node continuously scans the camera feed. Once the target object is detected, the system preempts the Nav2 behavior tree and dynamically hands control over to the IBVS visual servoing node, which smoothly drives the robot directly toward the object.1 This represents a highly sophisticated hybrid control architecture.

### **Phase 3: Edge AI and Embedded Intelligence (Days 31–45)**

Centralized processing introduces latency and power bottlenecks. Phase 3 distributes the intelligence by deploying lightweight machine learning models directly onto embedded hardware (the ESP32), bridging the microcontroller back to the central ROS2 graph.  
**Days 31–38: Model Quantization and TinyML Deployment**  
**Days 31–32: The TensorFlow Lite Ecosystem.** Deep learning models built in PyTorch or standard TensorFlow are too large for microcontroller SRAM. The developer will utilize the TensorFlow Lite (TFLite) Converter to compress a standard neural network into a .tflite flatbuffer.1 The curriculum covers the mechanics of graph optimization and operator fusion required to strip unnecessary bloat from the neural architecture.1  
**Day 33: Open Neural Network Exchange (ONNX).** To ensure framework agnosticism, the developer will export PyTorch models (such as the vision architectures from Phase 2\) into the ONNX format.1 Using the ONNX Runtime Python API, inference speed is benchmarked against the TFLite models to evaluate the optimal execution engine for edge deployment.1  
**Day 34: INT8 Post-Training Quantization.** The most critical step in TinyML is quantization. The developer will apply post-training INT8 quantization algorithms, converting the 32-bit floating-point weights (FP32) of the neural network down to 8-bit integers (INT8).1 This mathematical transformation compresses the model size by approximately 400% and drastically accelerates inference latency on devices lacking dedicated floating-point units (FPUs), all while maintaining an acceptable accuracy threshold.1  
**Days 35–36: Edge Impulse Studio.** The Edge Impulse platform abstracts the complexities of TinyML pipelines.1 The developer will utilize Edge Impulse to collect a custom dataset—such as physical hand gestures captured via a smartphone accelerometer or a connected IMU.1 A lightweight neural classifier is trained within the cloud studio, optimized for the Espressif ESP32 architecture, and exported as an executable C++ SDK.1  
**Days 37–38: TensorFlow Lite for Microcontrollers (TFLM).** The developer transitions to bare-metal programming, utilizing the PlatformIO IDE to integrate the exported Edge Impulse C++ library or a raw TFLM C-byte array onto the ESP32.1 The firmware is engineered to sample data from the physical sensors, allocate tensor arenas in memory, invoke the TFLite interpreter, and output local classifications.1 The "TensorFlow Lite With Platform.io and the ESP32" tutorial by atomic14 on YouTube provides the canonical walkthrough for this compilation process.42  
**Days 39–45: The micro-ROS Middleware Bridge**  
**Days 39–40: XRCE-DDS Agent and UDP Transport.** Microcontrollers lack the network stack required to participate directly in the standard ROS2 FastDDS graph. The developer will install micro-ROS, utilizing the Micro XRCE-DDS protocol.1 The ESP32 is flashed with micro-ROS firmware compiled via the Arduino IDE or PlatformIO.44 Simultaneously, the micro\_ros\_agent is launched on the Ubuntu 24.04 host machine to act as the bidirectional routing bridge.44 Crucially, the communication transport is configured for UDP over Wi-Fi, untethering the ESP32 from USB serial limitations and allowing it to function as a remote, wireless sensor node.3 Luis Cruz's YouTube tutorials on micro-ROS Jazzy for ESP32 S3 provide the exact procedural blueprints for this compilation.44  
**Day 41: IMU Sensor Publishing.** An MPU6050 6-axis Inertial Measurement Unit is physically wired to the ESP32's I2C pins. The micro-ROS firmware is programmed to continuously sample the accelerometer and gyroscope registers.1 These raw analog voltages are converted into standard metric units and packed into a sensor\_msgs/msg/Imu data structure.1 The ESP32 publishes this structure directly to the host's ROS2 graph over the Wi-Fi UDP bridge, making the physical hardware data instantly available to the Gazebo simulation.3  
**Days 42–43: Actuator and State Subscriptions.** Bidirectional communication is established. A micro-ROS subscriber is programmed into the ESP32 to listen for std\_msgs/msg/String or Bool topics generated by the host computer.1 Upon receiving specific commands (e.g., from the YOLOv8 perception node), the ESP32 triggers hardware interrupts to actuate physical GPIO pins, toggling LEDs or driving a servo motor.1  
**Days 44–45: Phase 3 Capstone Integration.** The TinyML inference and the micro-ROS transport layers are fused. The ESP32 utilizes the MPU6050 to capture a user's hand movements.1 The local Edge Impulse TFLite model classifies the movement as a specific gesture (e.g., "swipe left" or "tilt forward").1 The ESP32 then immediately publishes this semantic classification over micro-ROS.1 A node on the Ubuntu host maps these gesture classifications to geometry\_msgs/msg/Twist commands, allowing the user to teleoperate the simulated Gazebo robot using a physical, AI-powered wand.

### **Phase 4: Final Capstone Integration ("VisioBot") and Portfolio Building (Days 46–60)**

The final two weeks are dedicated to orchestrating the three massive domains—ROS2 simulation, computer vision, and edge AI—into a seamless, unified robotics pipeline suitable for professional presentation.  
**Days 46–48: System Architecture and Namespace Design.** The entire codebase is refactored into a production-grade ROS2 workspace. Packages are distinctly isolated into visbot\_vision, visbot\_navigation, and visbot\_firmware modules.1 The developer authors a master launch file capable of instantiating the Gazebo simulation, the Nav2 stack, the YOLOv8 perception nodes, and the micro-ROS agent simultaneously. Meticulous attention is paid to topic namespaces to prevent message collisions.1  
**Days 49–52: Multi-Domain Unification.** The operational logic is finalized. The ESP32 edge device, acting as an AI remote, dictates the high-level state machine of the robot.1 A gesture from the ESP32 commands the Gazebo robot to initiate a patrol sequence via Nav2. During patrol, the YOLOv8 pipeline actively analyzes the simulated camera feed. Upon detecting a designated target, the vision node overrides the Nav2 planner, executing the PID visual servoing control loop to approach the target dynamically.1  
**Days 53–55: Profiling, Optimization, and Debugging.** The system undergoes rigorous stress testing. The developer utilizes rqt\_graph to verify data paths and the ros2 topic hz command to monitor the publication frequency of the micro-ROS Wi-Fi packets, ensuring minimal UDP packet loss.1 The YOLOv8 inference latency is optimized to guarantee the visual servoing control loop receives data at a sufficient frequency to prevent kinematic oscillation. The RViz2 display is customized to provide an aesthetically pleasing, professional dashboard combining the 3D TF tree, the SLAM map, and the annotated camera feed.1  
**Days 56–57: Media Production and Repository Formatting.** A high-quality demonstration video is captured, utilizing split-screen editing to show the physical ESP32 gesture, the simulated Gazebo robot's reaction, and the internal RViz2 perception matrices simultaneously.1 The GitHub repository is structured to open-source standards, featuring an extensive README.md containing an architectural block diagram, dependency lists, and precise build instructions.  
**Days 58–60: Technical Writing and Professional Outreach.** The challenge concludes with the formulation of a comprehensive engineering article.1 The developer authors a detailed LinkedIn post and a medium-style blog dissecting the engineering hurdles overcome during the integration of ROS2 Jazzy, Gazebo Harmonic, and XRCE-DDS.1 On Day 60, the final showcase is broadcast on X/Twitter, directly tagging relevant corporate entities and encapsulating the 60 days of continuous learning.

## **Hardware and Software Setup**

The architectural philosophy of this challenge is simulation-heavy and hardware-light. Procuring a full robotic chassis involves prohibitive costs and mechanical delays; therefore, the hardware acts exclusively as an out-of-band edge intelligence controller.

### **Ubuntu 24.04 LTS Software Stack**

The foundation relies on a native installation of Ubuntu 24.04 LTS (Noble Numbat).2 Virtual machines or Docker containers, while feasible, introduce significant network complexities regarding the UDP multicasting required by FastDDS, as well as massive performance penalties regarding Gazebo Harmonic GUI rendering and PyTorch hardware acceleration.59

* **ROS Distribution:** ros-jazzy-desktop. This installs the necessary underlying DDS implementations, RViz2, and the ros2 CLI suite.4  
* **Simulation Dependency:** ros-jazzy-ros-gzharmonic. This package provides the essential bridging nodes that allow Gazebo Harmonic to communicate seamlessly with the ROS2 graph.13  
* **Vision Dependencies:** python3-opencv (OpenCV), ros-jazzy-cv-bridge (ROS-to-OpenCV translation), and the ultralytics pip package (for YOLOv8 instantiation).1  
* **Embedded Toolchain:** python3-colcon-common-extensions for ROS2 workspace building, alongside the PlatformIO IDE extension for VS Code to compile ESP32 firmware outside of the rudimentary Arduino IDE.41

### **Low-Cost Hardware Checklist**

1. **Microcontroller:** Espressif ESP32 Development Board (Preferably ESP32-WROOM-32 or ESP32-S3). The ESP32 provides a dual-core processor, sufficient SRAM for TinyML allocation, and a native Wi-Fi stack essential for untethered UDP micro-ROS communication.43  
2. **Inertial Measurement Unit:** MPU6050. A cheap, ubiquitous 6-axis accelerometer and gyroscope used to capture hand gestures or motion profiles.47  
3. **Range Sensor:** HC-SR04 Ultrasonic Distance Sensor. Useful for basic hardware interrupt testing.  
4. **Perception Hardware:** Standard built-in laptop webcam or generic USB UVC webcam. Avoid proprietary machine-vision cameras; standard webcams are universally compatible with the v4l2\_camera driver.22  
5. **Ancillary Components:** Standard 400-tie breadboard, male-to-male Dupont jumper cables, and a high-quality data-capable micro-USB/USB-C cable.

*Compatibility Note:* Ensure the Linux user profile is added to the dialout or tty groups to allow non-root permission to flash the ESP32 over /dev/ttyUSB0. When operating micro-ROS over Wi-Fi, ensure the host machine's firewall (ufw) is configured to allow incoming UDP traffic on the designated micro\_ros\_agent port.46

## **Portfolio and Capstone Guidance**

### **Framing "VisioBot" for the Industry**

When presenting VisioBot to corporate recruiters or research laboratories, the terminology is critical. It must not be presented as a simple "hobby robot." It should be defined as a **"Distributed Cyber-Physical System featuring AI-driven semantic perception and edge-computed hardware teleoperation."** The narrative must emphasize the architectural decoupling: heavy computational tasks (YOLOv8 spatial inference, SLAM pose-graph optimization, and Nav2 behavior trees) are handled by a high-performance central node, while low-latency hardware actuation and localized gesture inference (TinyML) are delegated to a resource-constrained edge device (ESP32) utilizing the XRCE-DDS protocol.1 This exact architecture mimics modern industrial IoT deployments and fleet-managed autonomous vehicles.

### **Final Deliverables**

To maximize internship appeal, the final portfolio must feature a highly organized, open-source GitHub repository containing:

1. **Code Segregation:** Workspaces cleanly partitioned into logical meta-packages (e.g., visbot\_perception, visbot\_navigation, visbot\_firmware).1  
2. **Architectural Diagrams:** Flowcharts generated via tools like Draw.io that map out the ROS2 node graph, explicitly illustrating the topic namespaces, message types, and the network bridge between FastDDS and Micro XRCE-DDS.  
3. **Visual Evidence:** A polished, 2-minute demonstration video utilizing split-screen editing. One side displays the physical ESP32 capturing a gesture; the other side displays the RViz2 interface updating the kinematic velocity, alongside the YOLOv8-annotated camera feed tracking the target in Gazebo.1
