# Tracker Tuning Guide: Handling Occlusion and ID Switching

When deploying object tracking algorithms in real-world or simulation environments (like our Gazebo setup), you will often encounter a common computer vision failure mode known as **ID Switching**.

## What is ID Switching?
ID switching occurs when a tracking algorithm assigns a new, unique identification number to an object it was already tracking.

In our Day 20 implementation, this happened when a tracked pedestrian (e.g., `person_2`) walked completely behind a fire hydrant. The bounding box disappeared because of **occlusion**. When the pedestrian emerged on the other side, the tracker suffered from "amnesia", failing to recognize that it was the same person, and assigned a new ID (e.g., `person_252`).

## Why Does it Happen?
Most modern trackers (like BoT-SORT) rely on two core components:
1. **A Kalman Filter:** This predicts where an object *should* be in the next frame based on its previous velocity and direction.
2. **Intersection over Union (IoU) & The Hungarian Algorithm:** This matches the predicted location of an object with the actual detection box generated by YOLO in the current frame.

### Common Causes of Failure:
- **Extended Occlusion:** The default tracker is only configured to remember a lost object for 30 frames (about 1 second at 30 FPS). If the person is hidden behind an obstacle for longer than that, their ID is wiped from memory entirely.
- **Fast Camera Ego-Motion:** If the robot turns abruptly, the background shifts. The Kalman filter predicts the person will be in Spot A, but because the camera moved, they appear in Spot B. The boxes don't overlap, so the algorithm assumes it's a completely different person.

## The Solution: ByteTrack and Increased Track Buffers
To fix this and make the tracker resilient to occlusion and camera movement, we need to adjust the tracking parameters.

1. **Switch to ByteTrack:** ByteTrack is often more robust during fast movements and partial occlusions because it associates low-confidence detection boxes (which happen when an object is partially hidden) with existing tracks, rather than simply discarding them like some other algorithms do.
2. **Increase the Track Buffer:** We can significantly extend the tracker's memory so it waits longer for an object to reappear before giving up.

### Custom Tracker Configuration (`custom_bytetrack.yaml`)
By passing a custom configuration file to Ultralytics, we can explicitly set these parameters:

```yaml
tracker_type: bytetrack  # Use the ByteTrack algorithm
track_high_thresh: 0.5  # Standard threshold for initial matching
track_low_thresh: 0.1  # Matches low-confidence boxes (crucial for partial occlusion)
new_track_thresh: 0.6  # Threshold to spawn a brand new ID
track_buffer: 120  # Remember lost tracks for 120 frames (4 seconds at 30 FPS)
match_thresh: 0.8  # IoU matching threshold
fuse_score: True  # Fuses confidence score with distance metrics
```

### Implementing the Fix
In your YOLO detector node, load the custom YAML file and pass it to the `tracker` argument:

```python
import os
from ament_index_python.packages import get_package_share_directory

# Get path to the config file installed via setup.py
visiobot_vision_dir = get_package_share_directory('visiobot_vision')
tracker_config = os.path.join(visiobot_vision_dir, 'config', 'custom_bytetrack.yaml')

# Run inference using the custom tracker
results = model.track(source=frame, persist=True, tracker=tracker_config)
```

By increasing the `track_buffer` to 120, VisioBot will now remember the pedestrian's ID for up to 4 full seconds while they are hidden behind the fire hydrant. When they emerge, the Hungarian algorithm will match them up flawlessly, completely eliminating the ID switching issue!
